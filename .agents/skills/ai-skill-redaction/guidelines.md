# Skill guidelines

The standard every skill under `.agents/skills/` follows (`.claude` is a symlink to `.agents`). It
is extracted from the hand-written skills of this repository and from the official guidance:

- [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
  (Anthropic)
- [Agent Skills specification](https://agentskills.io/specification), and its guides on
  [best practices](https://agentskills.io/skill-creation/best-practices),
  [scripts](https://agentskills.io/skill-creation/using-scripts) and
  [descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)

When a rule here and an existing skill disagree, the rule wins.

## 1. What a skill is for

| Question | Where it is answered |
| --- | --- |
| How does the system fit together? | [doc/](../../../doc/README.md) |
| What belongs in this directory, and what may it import? | That directory's `README.md` |
| How do I perform this task, step by step? | A skill |

A skill teaches an agent **how to do one task in this repository**: the steps, the files to touch,
the traps, and how to prove the result is right. It is loaded only when its description matches the
task, so it may be prescriptive where a README only describes.

Write one when:

- the same task comes back and needs the same project-specific steps every time;
- an agent got it wrong and had to be corrected — the correction is the skill's most valuable line;
- a convention spans several files that must change together (a config entry, an endpoint, a page).

Do not write one for what the agent already does well without it. Every line competes for context:
for each sentence ask "would the agent get this wrong without it?" and cut it if the answer is no.

Scope a skill like a function: one coherent unit of work. Too narrow and a task needs five skills
that contradict each other; too broad and it triggers on everything. `backend-config-entry` is the
right size: one setting, three files, one checklist.

## 2. Name

The `name` is the directory name: lowercase letters, digits and single hyphens, at most 64
characters, no leading or trailing hyphen.

It starts with a **scope prefix**, so related skills sort together and the scope is clear at a
glance. The list is not closed: add a prefix when a new area appears, and use it consistently.

| Prefix | Scope | Example |
| --- | --- | --- |
| `frontend-` | The React app under `frontend/` | `frontend-page` |
| `backend-` | The Rust crates under `crates/` and the binaries | `backend-config-entry` |
| `infrastructure-` | `infrastructure/`: Docker, Compose, Kubernetes, Nix, CI/CD | `infrastructure-docker-image` |
| `doc-` | Anything Markdown or user-facing documentation: READMEs, user guides, developer docs, docstrings, schemas | `doc-readme-redaction` |
| `ai-` | Anything about agents themselves: skills, agent definitions, prompts, `CLAUDE.md` | `ai-skill-redaction` |
| `api-` | API documentation skills generated by `openapi2skill` | `api-backend` |

After the prefix, name the task, not the tool: `backend-database-migration`, not `backend-sqlx`.
Avoid vague words (`helper`, `utils`, `misc`) and the reserved words `anthropic` and `claude`.

`api-*` skills other than `api-skill-generator` are generated: never edit them by hand, regenerate
them with Skill(api-skill-generator).

## 3. Frontmatter

```yaml
---
name: backend-config-entry
description: Use when adding, renaming or removing a configuration setting of the Rust backend (crates/config).
---
```

Only `name` and `description` are expected. Add `allowed-tools` only when the skill must run with a
restricted tool set (as `api-skill-generator` does), and `compatibility` only for a hard
environment requirement.

### Description

The description is the only part of the skill an agent sees before deciding to load it. It carries
the whole burden of triggering.

- **One line, starting with `Use when`** (or `Use after` / `Use before` when timing is the
  trigger). This repository uses the imperative form the Agent Skills guide recommends; it tells the
  agent when to act. Anthropic's guide asks for the third person instead — both are fine, and
  consistency within the repository matters more, so keep `Use when`.
- **List the triggers, not the mechanics**: the user's intents (`adding, renaming or removing`),
  the paths (`crates/config`, `src/components`), the file names, and the check that fails
  (`fixing an i18n:check failure`, `when scripts/test_openapi.sh fails`).
- **Cover the indirect asks.** A user rarely says "frontend-page"; they say "add a screen". Name the
  synonyms: `a page, route or screen`.
- **Exclude the near-misses** when a neighbour skill could also match: `a Rust src/ file under
  crates/` keeps `backend-unit-test-location` from firing on `crates/*/tests/`.
- Stay under 200 characters in practice. The hard limit is 1024.

## 4. Directory layout

```txt
<name>/
├── SKILL.md          # the instructions, always loaded with the skill
├── <topic>.md        # extra detail, read only when SKILL.md says so
├── assets/           # boilerplate to copy: endpoints.rs, trait_tests.rs, Cargo.toml
└── scripts/          # deterministic checks: check_<thing>.sh
```

Extra `.md` files sit next to `SKILL.md`, named after their topic (`nested-routes.md`,
`internals.md`, `install.md`), never `doc2.md` or `more.md`. Each one is linked **directly** from
`SKILL.md` — one level deep, never a chain of files linking to files.

## 5. SKILL.md body

```txt
# <Verb> <thing>

<One to three sentences: what the task is, the invariant that makes it non-obvious, and the
README to read first.>

<Optional: a tree or a flow diagram in a txt block.>

## 1. <Imperative step>
## 2. <Imperative step>
...
## <Topic>              optional: "Never", "Rules", "Notes", "Which double for which test"
## Checklist            always last
```

Model it on the existing skills:

| Writing a skill that | Model it on |
| --- | --- |
| Changes several files in a fixed order | [backend-config-entry](../backend-config-entry/SKILL.md) |
| Scaffolds with a generator, then checks with a script | [frontend-page](../frontend-page/SKILL.md) |
| Ships copyable boilerplate in `assets/` | [backend-add-api-endpoint](../backend-add-api-endpoint/SKILL.md) |
| Wraps an external CLI with a prerequisite | [api-skill-generator](../api-skill-generator/SKILL.md) |

### Title and opening

The title is the task as a verb phrase: `# Add a backend configuration entry`,
`# Write a commit message`. The opening states the one fact that makes the task worth a skill:

> A setting must be declared in three files before it reaches the backend. Miss one and the
> setting parses fine but is never used, with no compiler error.

Point to the README instead of repeating it: "Read [crates/config/README.md](…) first for the
`CliConfig` / `Config` split."

### Steps

- Number them: `## 1. Declare the default`. Each heading is an imperative the agent can act on.
- One step, one action. Put the exact command or the exact code shape in a block right under it.
- **Use real code from the repository**, not invented examples, and name the file to copy:
  "[src/pages/User/sections/ApiKeys](…) is the reference to copy."
- **Give a default, not a menu.** "Use `AppLayout`. `AuthLayout` is for `/auth/*` only." beats a
  list of equal options.
- **Match strictness to fragility.** A fragile sequence gets the exact command and "do not modify
  it"; a judgement call gets the goal and the reason.
- **Say why** in a clause after the rule: the reason lets the agent handle the case the rule did
  not foresee.
- Mark optional steps in the heading: `## 4. Validate, only when there is a rule`.

### Gotchas

The highest-value lines in a skill are the concrete corrections to mistakes an agent will make:

- "an omitted body generates as `unknown` and silently weakens the frontend's error typing"
- "a bare `cargo test -p database` silently skips it"

Keep them in `SKILL.md`, next to the step they concern, or in a `## Never` / `## Notes` list. Every
time an agent has to be corrected on a task, add the correction to its skill.

### Cross-references

- Another skill: `Skill(<name>)`, inline where it is needed — "Data comes from `api/hooks/` —
  Skill(frontend-api)."
- A repository file: a relative link from the skill directory, `../../../crates/config/src/cli.rs`.
- A file of this skill: `[nested-routes.md](./nested-routes.md)`, with **when** to read it: "For
  child routes and sub-navigation, read nested-routes.md." A reference file that is only needed
  in a rare case says so: "Do not read it otherwise."
- A tool the skill depends on: a `## Prerequisite` section — "Consider it installed, but if the
  command is not found follow `[install.md](./install.md)`, then resume your task."

### Content rules

- **Only what the agent lacks**: project conventions, paths, commands, traps. Never explain what
  Rust, a migration or an HTTP status is.
- **One term per concept**, used everywhere: once a trait's implementations are called
  "backends", never call them "implementations" or "providers" further down.
- **Nothing time-sensitive.** No "after the v2 migration" or dates. Describe what is true now.
- **No duplicated rules.** A rule lives in one README or one skill; others link to it.
- No emojis. Plain words and short sentences, as in the README guidelines.

## 6. Prefer deterministic tools over judgement

**An agent reading a file and judging it is slow, costly and can be wrong. A script is instant and
says the same thing every time.** So whenever a rule of a skill can be checked by a program, it is
checked by a program, and the skill tells the agent to run it.

Pick the strongest place a rule can live, top first:

1. **The compiler or the type system** — a type that makes the wrong state unrepresentable, a
   `compile_fail` fixture (`test_trait_derive` pins its errors with `trybuild`).
2. **An existing linter or check** — an ESLint boundary rule, Clippy, `bun run i18n:check`,
   `bun run seo:check`, `./scripts/test_openapi.sh`.
3. **A repository script** under `scripts/test_*.sh` — for a rule that holds across the
   repository; the `pre-push` hook runs every one of them.
4. **A skill script** under `<skill>/scripts/check_*.sh` — for a rule about the result of one task
   (`check_page.sh <PageName>`).
5. **A checklist item** — only for what genuinely needs judgement.

When writing or updating a skill:

- **Use** the tools that already exist: list them in the checklist rather than describing what they
  check.
- **Write** a script as soon as a rule is mechanical (a file exists, a name matches, a line is
  present, two files agree) or as soon as an agent keeps re-deriving the same check by hand.
- **Update** the script in the same change as the rule. A script that checks an old rule is worse
  than none.
- **Never** turn a scripted check back into prose.

### Writing a check script

Follow the [scripts/README.md](../../../scripts/README.md) header and the shape of
[check_page.sh](../frontend-page/scripts/check_page.sh):

```bash
#!/usr/bin/env bash
set -e

GIT_ROOT=$(git rev-parse --show-toplevel)
cd "$GIT_ROOT"

# Verifies a page is complete and wired into the router.
# Usage: .claude/skills/frontend-page/scripts/check_page.sh <PageName>

PAGE=${1:?usage: check_page.sh <PageName>}
```

- Make it executable, and call it from the repository root by its full path:
  `.claude/skills/<name>/scripts/check_<thing>.sh`.
- **Never prompt.** Take every input as an argument, and fail with the usage line when one is
  missing.
- **Read-only and repeatable.** A check changes nothing, so it can be run any number of times.
- **One line per check**, `✓` or `✗`, then a summary. The failure line names the file and the fix:
  "`$hit` hand-writes `#[path = "_tests/..."]`; use `test_utils::tests_file!` instead".
- **Exit 1 on any failure**, 0 otherwise, so it can gate a hook or CI.
- Keep the output short; an agent's tool output gets truncated.
- Justify every constant in a comment. A limit nobody can explain is a limit nobody can fix.

## 7. Checklist

Every skill ends with `## Checklist`. It is the agent's proof that the task is done, so it comes in
two parts, in this order:

1. **A `bash` block of the commands to run**: the skill's scripts first, then the existing checks.
   When one command matters more than the others, say which one and why.
2. **`- [ ]` items for what no command can check**: a judgement call, a review of wording, a
   decision. Keep two to five of them.

````md
## Checklist

```bash
.claude/skills/frontend-page/scripts/check_page.sh <PageName>
cd frontend && bun run i18n:check && bun run seo:check
```

- [ ] The page sits under the right layout, and behind `ProtectedRoute` if it needs a session.
- [ ] Nothing outside the page folder imports its internals.
````

Each item is checkable, starts with the expected state, and does not restate a step. An item a
script could verify is a script waiting to be written: write it, then delete the item.

## 8. Size and formatting

- `SKILL.md` stays under **500 lines**; most skills here are 60–150. Past that, move a rare branch
  into a `<topic>.md` and link it with the condition to read it.
- Formatting follows the [README guidelines](../doc-readme-redaction/guidelines.md#5-formatting): prose
  wrapped at 100 characters, a language on every code block, nested bullets indented by 4 spaces,
  compact tables, relative links.
- Forward slashes in every path.

## 9. Wiring a skill in

- Add it to the `## Skills` section of the README of every directory it applies to. A skill no
  README links to is only found through its description.
- For a frontend skill, add it to the `Agents:` list in [frontend/README.md](../../../frontend/README.md).
- If it must run on every occurrence of a task regardless of wording, add a one-line rule to the
  root `CLAUDE.md`, as is done for `doc-readme-redaction`.
- Commit it with the `ai` type: `ai(skill): add frontend-form` — Skill(commit-messages).

## 10. Testing a skill

A skill is code for an agent: it is tested by running it.

1. **Before writing**, run the task without the skill and note what goes wrong. Those failures are
   what the skill must fix; anything else is noise.
2. **After writing**, run a real task with the skill in a fresh session and read the trace, not
   only the result. An agent that tries several approaches means a step is vague; an agent that
   follows an instruction that did not apply means the instruction needs a condition.
3. **Check the triggering**: a few prompts that should load the skill, worded the way a user would
   (without its name), and a few near-misses that should not.
4. Feed every correction back as a gotcha or a script.
